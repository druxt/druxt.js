'@druxt/client': major
---

feat(#979)!: add `@druxt/client`, the JSON:API client split out of 1.x's `druxt` package, with no Vue, Nuxt or HTTP dependency.

Requests go through the Fetch API: the `fetch` and `headers` options replace the Axios instance, and an `axios` option is ignored. The 0.25.0 cache behaviour carries over: the Cache-Control-aware process cache, the bypass for credentialed and session-cookie requests, `cache.ttl` and `clearCache()`. With `cache.content`, a `bypassCache` read's answer replaces the stored entry when it may be stored. Any other answer, such as a 404, removes the entry, so the next read never gets the older document. A request that never reaches Drupal leaves the entry. An answer to a read that started before the one whose answer was stored, or removed the entry, isn't kept. Each set of client headers keeps its own entries, and a response or an index whose request was in flight when the client's headers changed is stored under neither set. `cache.maxSize` bounds each cache area across all its sets: an area holds one kind of answer, such as the content or a module's menus. Past it the area's least recently used entries go, whichever set holds them. An area also keeps a fixed number of sets, the least recently used going first. druxt-auth's OAuth flows live here now: PKCE, the password and client credentials grants, token refresh, and a retry after a 401. `auth.refresh.share` shares a refresh between clients holding one session, as a server's renders of one browser do.

A resource URL for a type the JSON:API index does not list now keeps the language prefix, and `getCollection` fetches that fallback URL instead of returning `false`.

`getResource()`, `getRelated()`, `createResource()` and `updateResource()` throw a `TypeError` naming an empty type, id or related field name. 1.x returned `false`.

`getCollection()` and `getCollectionAll()` throw a `TypeError` on an empty type. 1.x requested the bare JSON:API endpoint.

`createResource()` and `updateResource()` send the POST or PATCH for a type the index does not list. A type Drupal does not expose rejects with the request's `DruxtError`. 1.x returned `false` without sending anything.

A `baseUrl` in the options wins over the constructor's argument, as in 1.x, and requests now go to it too. 1.x's Axios instance sent them to the argument.

`getIndex(type)` and `auth.getUser()` answer `undefined` instead of `false`, and `addHeaders()` returns nothing.

`auth.session` is for a browser whose site's server holds the tokens, in httpOnly cookies, behind a proxy that adds the `Authorization` header. The client then holds only the `druxt.auth.session` marker and sends no `Authorization` header. It refreshes through `tokenUrl`, with no refresh token of its own, and signs out through `logoutUrl`. A request made with `auth: false` asks the proxy for no credentials with `X-Druxt-Auth: none`. A signed-in session-mode client never reads or writes the process cache, on a server too. `auth.logout()` returns a promise. Under `auth.session` it posts to `logoutUrl` first and forgets the session only once that route answers with a 2xx; otherwise it rejects with the request's error and the session is kept. A logout that succeeds ends the session, even one a sign-in stored while the route ran, and a sign-in or refresh still waiting stores nothing. The next sign-in starts a new session.

A refresh token Drupal refuses, with a 400 or a 401, ends the session, and a read refused with it is repeated as the anonymous visitor, asking the proxy for no credentials under `auth.session`, while a write is not. A write whose token had already expired, refused before it is sent, isn't sent at all: it rejects with the refusal, the token request's error with a 400 or a 401. Other refresh failures, such as a timeout, keep the session. If Drupal refuses an access token with a 401 and there is no refresh token to try, a read sent to Drupal ends the session and is repeated anonymously. A write, or another host's 401, does neither. The session of a sign-in made while a refused refresh or read was pending is kept. A sign-in or refresh that a later sign-in or a sign-out replaced while it ran stores nothing. When it succeeded, it rejects with an error whose `superseded` is true, which `isSuperseded()` tells from a failure, and when it failed, it rejects with its own error. A session signed in while the last one's refresh ran refreshes on its own, and never waits on that one's answer, with `auth.refresh.share` too. A request goes to Drupal only as the session it was made for. If another session signs in while it waits on a refresh, it rejects with the superseded error and is not sent, and a 401 answered after another session signed in is returned as it is, with no refresh or retry. A request whose session a sign-out ended is sent without a token, as a signed-out client's requests are. A sign-in, whatever its grant, ends the session held before it as it starts, so a visitor who tries to sign in as someone else is never left signed in as the user before, whether it fails, as druxt-auth 0.x had it, or succeeds. A request made while it runs goes without a token, and its 401 is returned as it is. Under `auth.session` the session before is in the site's cookies, which the site's proxy adds until the sign-in at `tokenUrl` answers. Druxt's Nuxt module doesn't start a sign-in while a session is held. A session signed in within `auth.refresh.grace` of the last session's refresh still refreshes on its own.

The access token goes only to the origin the client sends Drupal's requests to: the base URL's, or the page's own when the API is proxied. So do the `Authorization`, `Proxy-Authorization` and `Cookie` headers set with `headers` or `addHeaders()`, such as a Basic `Authorization`. A request to another host is sent without them, and its 401 is returned as it is, with no refresh or retry. Other headers set with `headers` or `addHeaders()` go to every host, and a header passed to the request itself is sent as given.

`auth` is `undefined`, not `null`, when auth is off. `processCache()` answers `undefined`, not `null`, when the cache must not be used.

BREAKING CHANGE: `DruxtClient` is imported from `@druxt/client`, and the Axios instance and every `axios` option are gone, `axios.headers` among them: set headers in `headers`.

`DruxtClient` no longer has a `settings` property holding the module settings. `clientOptions()` picks the client's options out of a site's config, and `resolveDruxtSettings()` merges the module settings from several sources.

`connectionsFrom()` builds the `default` connection from a site's flat config. A connection has one `consumer` (the Simple OAuth client, from `build.auth` or else `auth.clientId`), and an optional `browser` sign-in override. Any connection under another name is listed as ignored, because those names are reserved for 2.1.0. A module that reads decoupled settings names the Consumer in an option of its own, since the client has none. `clientOptions()` takes a connection or the flat config and returns a deep copy, and never copies a Consumer's secret.

An `onRequest` option and `client.onRequest()` report each request's method, URL, status and duration, for logging and metrics. They see no headers or bodies, and secret query values such as `token` and `code` are emptied from the URL.

A request listener's `end` event carries `omitted`, Drupal's reason, when Drupal omitted resources from the response. With `warnOmitted`, the client warns once per omitted resource type for each site until `clearCache()`, with `DRUXT_E01001`, naming each type the omitted items' links name and quoting the reason. `omittedResources()` reads what a document omitted, its reason and each omitted type and id, without the links.

`prefixes` maps each langcode to the URL prefix Drupal serves it under, `{ en: '', es: 'spanish' }`, so a method's `prefix` argument takes a langcode as well as a prefix. A langcode the map lacks is used as the prefix itself, as before. `urlPrefix()` gives the mapping.

A nested null in a query object is left out of the query string, as an `IS NULL` condition must have no value.

A request body that is a plain object or an array is sent as JSON:API JSON. A `Blob`, a buffer, a typed array, `FormData` or a stream is sent as it is, as 1.x's Axios sent it, for a file upload. A `ReadableStream` or an async iterable, a plain object with a `Symbol.asyncIterator` method too, goes with `duplex: 'half'`, which fetch requires for a stream body, and needs a fetch that can upload a stream, as Node's can and some browsers' can't. A stream is consumed as it is sent, so it's never sent twice. A 401 to it still refreshes the session, and the 401 stands for the caller to retry with a new stream.
