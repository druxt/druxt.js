feat(#980)!: add `@druxt/core`, the Druxt module for Nuxt 4, in place of the `druxt` package.

The store runs on Pinia, and `useDruxtClient()` gives a component the configured client. `useDruxtStore()` is auto-imported, and its `peekResource()` and `peekResources()` read what the store holds, with no request, during a render.

The store's `getResource()` throws a `TypeError` naming an empty type or id. 1.x returned an empty object. `druxt.auth.password` turns the password sign-in on or off. Unset, a build secret or a Consumer of its own turns it on. Off, the token route refuses the password grant, and stays only for a session the server holds, for its code grant and refresh. The route sends a secret only when one is set, so a site whose secret arrives at runtime, or whose Consumer is public, sets `password: true`. With `proxy.api` on, the tokens leave JavaScript: the token route keeps them in `httpOnly` cookies on the site's host, `Secure` on an https site, and the proxy sends the access token to Drupal as the `Authorization` header. The browser reads only `druxt.auth.session`, the token's expiry. The authorization code grant and the refresh go through the token route, `POST /api/_druxt/auth/token`, too, and `POST /api/_druxt/auth/logout` signs out. A sign-in through the client itself, `$druxt.auth.loginWithPassword()`, ends the session the browser had as it asks Drupal, as 0.x did, so one Drupal refuses leaves the browser signed out, never signed in as the user before. Server renders for one browser that need a refresh at once, such as tabs opening together after Drupal revoked the visitor's access token, share one refresh within the server process, as Simple OAuth accepts a refresh token once. `auth.exposeToken: true` keeps the tokens readable by the page's scripts, as 0.x did, for a module that calls Drupal outside the proxy: a weaker setting. The proxy sends Drupal only its own session cookie, `SESS` or `SSESS` and a hash, or the name `cache.sessionCookie` matches. druxt-auth 0.x's proxy sent every cookie the browser held, so a site's other cookies, Druxt's `druxt.auth.*` and nuxt-auth-utils' `nuxt-session` among them, now stay on the site. A token too large for a browser's cookie, past 4096 bytes, doesn't set a cookie: the sign-in is refused with a 502 and `DRUXT_E01007`, and a refresh that answers one ends the session.

`druxt.siteUrl` names the site's public origin for links a page emits about itself. It defaults to an empty string, so `NUXT_PUBLIC_DRUXT_SITE_URL` can set it on a site that does not declare it in `nuxt.config.ts`.

The module splits `druxt` once. Secrets move to the private `runtimeConfig.druxt`, and the rest is public at `runtimeConfig.public.druxt`. Read settings with `useDruxtSettings()`, and on the server with `useDruxtServerSettings(event)`. A decoupled-settings fetcher hands settings from Drupal to `storeDrupalSettings()` or `setDrupalSettings()`, and the config wins over them. A fetcher module names the Consumer it reads for in an option of its own, such as `druxt.site.settingsConsumerId`. Core has none. `setDrupalSettings()` merges the public tier over the stored one, so a runtime fetcher keeps what the server stored at start, and `{ replace: true }` replaces it instead. Module settings are no longer client options.

A Druxt module registers its default settings with `addDruxtDefaults()` from `@druxt/core/kit`. The build holds them, and neither an environment variable nor the public runtime config changes them. They resolve after core's defaults and before the settings Drupal publishes and the site's config, so Drupal can change a module's default too.

`useDruxtAnonymousClient()`, from `@druxt/core/server`, gives a server route a client that reads Drupal as a visitor.

Under pnpm, `nuxt dev` works without adding the module's CommonJS libraries to your own dependencies.

BREAKING CHANGE: install `@druxt/core` in place of `druxt`. The module runs on Nuxt 4 and Vue 3 only, the store is Pinia, and the options-API `DruxtModule` and the mixins are gone from core. The private runtime config keys `druxtAuth`, `druxtCache` and `druxtBuild` are now `druxt.auth`, `druxt.cache` and `druxt.build`, and the environment variable names are unchanged.

`getResource()` waits for a request already in flight for the same resource with another query, unless the store already answers, so a second reader of one entity, such as a standalone field beside its entity, is answered from the store. A request with the same query is shared, its failure included.

The proxy reads `druxt.baseUrl` from the runtime config for each request, so a build pointed at another Drupal with `NUXT_PUBLIC_DRUXT_BASE_URL` sends the browser's JSON:API, file, token and userinfo requests to the same Drupal as the server. They went to the build's Drupal before. The JSON:API is proxied under the language prefixes Drupal is configured with, such as `/english` for `en`, and a default language with no prefix is served unprefixed. `getLanguages()` returns each language with its prefix, and `getLanguagePrefixes()` returns the configured prefixes. A Druxt module proxies a path of its own with `addDruxtProxy()` from `@druxt/core/kit`. The proxy streams request bodies. Drupal's redirects reach the browser, with a location on Drupal's base URL moved to the site, and its cookies are set for the site's host. The forwarding headers come from the site's own view of the request, and any the browser sent are dropped. Behind a front proxy the site trusts, `proxy.trustForwarded`, or `NUXT_DRUXT_PROXY_TRUST_FORWARDED` at runtime, passes that proxy's forwarding headers on and adds the visitor to its `X-Forwarded-For` chain. It is private runtime config, never sent to the browser. The build reads the prefixes without credentials, once for every module, and a failed probe falls back to the langcode with a warning. A read that fails outright, such as with build credentials Drupal refuses, warns once, and the proxy then serves only the unprefixed endpoint. It reads the anonymous index first, so a site without the language module costs one request and no sign-in. Druxt's own server routes sit under `/api/_druxt`, `DRUXT_API_BASE` from `@druxt/core/routes` and `@druxt/core/kit`, and answer before the proxy, so a Drupal that serves JSON:API at `/api` keeps them. The proxy sends Drupal no path under `/api/_druxt`, and answers 404 for one that no Druxt route takes, such as a `GET` to a `POST` route. A session cookie that doesn't decode, such as a bare `%`, counts as none, so the request goes on anonymously. In the browser, a session marker cookie that doesn't decode reads as signed out. A JSON:API endpoint at or under `/api/_druxt`, with or without a language prefix, fails the build with `DRUXT_E01006`.

`getLanguages()` marks the default language, the one Drupal answers in at the unprefixed endpoint, with `default: true`. It reads each language's configured prefix from `language.negotiation` when the decoupled_settings module publishes it, and the client on both sides gets the map, so a module's langcode reaches Drupal under the prefix it is served at.

The store's `addResource()` and `addCollection()` take `partial`, so a module seeding a view's rows records the fields each holds, and a later read of another field fetches it. A resource with no self link is still stored. An included resource, at any depth, is stored with every field, so a sparse read of it comes from the store. The store doesn't keep Drupal's `links` on resources, relationships or collections, so a page's payload doesn't name backend URLs. What Drupal omitted is kept as its reason and the omitted types and ids.

`createDruxtConfigHold()`, from `@druxt/core/server`, holds site configuration read from Drupal once per build and key in Nitro storage until a Druxt cache clear, with shared concurrent reads and a window for a failed one. A hold's name, with no colon or slash, keeps its keys apart from another's, and a read of `undefined` is held as `null`. Each consumer clears its own hold on the `druxt:cache:clear` Nitro hook, as entity does for Drupal's date formats, which it holds under the name `date-formats`.

The store's `peekMeta()` gives the `meta` of the document a resource came in, such as what Drupal omitted, with no request. A stored resource's includes skip the resources Drupal already denied, and omitted links are read against the client's JSON:API path.
