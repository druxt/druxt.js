feat(#980)!: add `@druxt/core`, the Druxt module for Nuxt 4, in place of the `druxt` package.

The `druxt: {}` contract, `DruxtWrapper` and wrapper resolution by name work as they did, on Vue 3 composition. A module calls `useDruxtModule(props, contract)` in `setup()`, and its data loads through Nuxt's `useAsyncData`, so the payload, hydration and refresh are Nuxt's own. A wrapper is a `<script setup>` component that declares the props it wants. A module renders no wrapper element unless asked for one, and passes a wrapper only the data it declares. `<Druxt module>` renders any module and passes `v-model` through. The store runs on Pinia, and `useDruxtClient()` gives a component the configured client. `useDruxtStore()` is auto-imported, and its `peekResource()` and `peekResources()` read what the store holds, with no request, during a render. A module's model is Vue's `useModel()`, so a wrapper reads it with `defineModel()`, and a contract's `restore()` hook sets it again in the browser after hydration.

A module can be a `<script setup>` component. Its name comes from the file name, so set `defineOptions({ name })` unless the file name is the full module name, as it is not for a file in a subdirectory. It renders what `useDruxtModule()` returns as a component in its template. In development, a module with no name, a module whose file name is not its registered name, and a module that never renders are each reported. A module's hooks run outside the Nuxt context after an await, so they get the client and the store as `ctx.client` and `ctx.store`. In production, `<Druxt>` logs a misspelled module once on the server, and renders nothing for it. `DruxtDebug` renders nothing in a production build, whatever its `visible` prop says, and a module that fails in production renders no markup for the failure.

In development, a Druxt tab in Nuxt DevTools lists the page's modules, missing wrappers, quiet errors, requests and settings, and offers to create a missing wrapper from its candidate names, written to `components/druxt/` and opened in the editor. The dev server route that writes it answers a request from another origin with a 403, including an `Origin` that doesn't parse, such as a sandboxed frame's `null`. It refuses a settings path through a name every object inherits, such as `__proto__` or `constructor`, and a path that is both a setting and the parent of others. A created field wrapper renders every value through one `<slot>` in a `v-for`, and declares only what its template reads, so it lints clean. The tab's icon is served from a dev server route, as Nuxt DevTools shows an image only from a path. The Requests section labels the server render's requests with the page they were made for, and lists them on that page alone. A kiosk, or any page with no visitor input, never lists them on a later path. A navigation to a hash in the same page keeps them under any `app.baseURL`. Vue DevTools gets a Druxt inspector and a timeline layer, and the console prints the defaults in use, with any quiet errors in a group of their own. Nothing is added to the page. An unknown `develMessages` value, such as 1.x's `'indicator'`, warns once at build, naming `'devtools'` and `'inline'`. The tools come from `@druxt/devtools`, an optional peer dependency a site adds as a dev dependency, and development without it prints one line saying so. A module adds its own sections, timeline events and actions with `useDruxtDevtools()`, from a plugin it registers with `addDruxtDevtoolsPlugin()`, and every call does nothing outside development. The cache-clear route keeps its secret out of the browser. The route that writes the file answers only a connection from the same machine.

In development, core loads a stylesheet for the inline create action and `DruxtDebug`, with ten `--druxt-*` tokens a site overrides on `:root`. Its colours follow the page's colour scheme, light unless the page declares `color-scheme: dark` or a `data-theme="dark"` ancestor, never the reader's system preference alone. It also gives entities and fields readable defaults, in the `druxt` cascade layer, so any rule the site writes outside a layer wins. A hidden field label's rule sits outside the layer, so a site rule can't reveal it to sighted readers by accident. A production build has none of it.

A module's data is keyed by its name, language and inputs, so `nuxt generate` gives every page its own data and two modules with the same inputs share one request. Each of them restores the shared data and calls `restore()`, in a server render as in the browser, so a menu in the header and the footer renders in both. A module's `watch()` inputs now form its data's identity, so list every input its data depends on, or give the contract a `key()`. The language is appended to a contract `key()`. A `restore()` that answers `false`, because the stores lack what the state names, runs the pipeline again before the server renders and at once in the browser. Under Nuxt's shared prerender data, a later page gets an earlier page's entry with stores of its own that start empty, so a menu in the layout renders on every prerendered page.

The store's `getResource()` throws a `TypeError` naming an empty type or id. 1.x returned an empty object. A query takes its `include` and `sort` as a list too, such as `include: ['uid']`, and as `include[]=uid` in a query string. 1.x threw on both. `getResource()` also reports a failed request as `error` on its result instead of hiding it, and the development tools list each module once per candidate set with a count. `useDruxtAuth().fetchUser()` resolves `undefined` when no one is signed in, and its `user` state holds `null`. The `druxt-auth` route middleware never lets a signed-out visitor through. It sends them to the login page, or to `/login` when `druxt.auth.login` is `false`, as 0.x did. A sign-in returns to the `redirect` it was given only when that is a path on the site, and to the front page otherwise. While the visitor is signed in, `DruxtAuthLogin` shows who is signed in and a sign-out button in place of the form, and signs no one in until they sign out. A `DruxtAuthLoginSignedIn` wrapper replaces that state. The login page and the callback page send a visitor who is already signed in on to where they were going, with no new sign-in. `useDruxtAuth().loginWithPassword()` and `loginWithDrupal()` refuse too, wherever a site calls them: while the visitor is signed in they send nothing, and the session and `user` stay as they are. They reject with an error whose `name` is `DRUXT_AUTH_SIGNED_IN`, a constant auto-imported with `useDruxtAuth()`, so a site tells the refusal from a failed sign-in by the name. To sign in as someone else, sign out first: `await useDruxtAuth().logout('/user/login')`. `druxt.auth.password` turns the password sign-in on or off. Unset, a build secret or a Consumer of its own turns it on. Off, the token route refuses the password grant, and stays only for a session the server holds, for its code grant and refresh. The route sends a secret only when one is set, so a site whose secret arrives at runtime, or whose Consumer is public, sets `password: true`. With `proxy.api` on, the tokens leave JavaScript: the token route keeps them in `httpOnly` cookies on the site's host, `Secure` on an https site, and the proxy sends the access token to Drupal as the `Authorization` header. The browser reads only `druxt.auth.session`, the token's expiry. The authorization code grant and the refresh go through the token route, `POST /api/_druxt/auth/token`, too, and `POST /api/_druxt/auth/logout` signs out. Both routes take requests from the site's own pages only. A request whose `Origin` names another host answers 403, so another site's form can neither sign a visitor in nor out, and with no `Origin` the `Sec-Fetch-Site` header decides. The site's host is the request's `Host`, or `druxt.siteUrl`'s when set, so behind a front proxy that sends another `Host`, set `siteUrl`, or `proxy.trustForwarded` for its `X-Forwarded-Host`. A sign-in through the client itself, `$druxt.auth.loginWithPassword()`, ends the session the browser had as it asks Drupal, as 0.x did, so one Drupal refuses leaves the browser signed out, never signed in as the user before. Server renders for one browser that need a refresh at once, such as tabs opening together after Drupal revoked the visitor's access token, share one refresh within the server process, as Simple OAuth accepts a refresh token once. `auth.exposeToken: true` keeps the tokens readable by the page's scripts, as 0.x did, for a module that calls Drupal outside the proxy: a weaker setting. The proxy sends Drupal only its own session cookie, `SESS` or `SSESS` and a hash, or the name `cache.sessionCookie` matches. druxt-auth 0.x's proxy sent every cookie the browser held, so a site's other cookies, Druxt's `druxt.auth.*` and nuxt-auth-utils' `nuxt-session` among them, now stay on the site. A token too large for a browser's cookie, past 4096 bytes, doesn't set a cookie: the sign-in is refused with a 502 and `DRUXT_E01007`, and a refresh that answers one ends the session. On Simple OAuth 6 the scope list is the role list, so a browser sign-in with no `druxt.auth.scope` warns at build with `DRUXT_E01004`, and in development a read refused to the signed-in visitor that an anonymous one may make is noted in the Druxt DevTools tab.

`druxt.siteUrl` names the site's public origin for links a page emits about itself. It defaults to an empty string, so `NUXT_PUBLIC_DRUXT_SITE_URL` can set it on a site that does not declare it in `nuxt.config.ts`.

The module splits `druxt` once. Secrets move to the private `runtimeConfig.druxt`, and the rest is public at `runtimeConfig.public.druxt`. Read settings with `useDruxtSettings()`, and on the server with `useDruxtServerSettings(event)`. A decoupled-settings fetcher hands settings from Drupal to `storeDrupalSettings()` or `setDrupalSettings()`, and the config wins over them. Overlapping `storeDrupalSettings()` calls for one connection write one after another within a server process, so a call per tier keeps both tiers. A fetcher module names the Consumer it reads for in an option of its own, such as `druxt.site.settingsConsumerId`. Core has none. `setDrupalSettings()` merges the public tier over the stored one, so a runtime fetcher keeps what the server stored at start, and `{ replace: true }` replaces it instead. Module settings are no longer client options.

A Druxt module registers its default settings with `addDruxtDefaults()` from `@druxt/core/kit`. The build holds them, and neither an environment variable nor the public runtime config changes them. They resolve after core's defaults and before the settings Drupal publishes and the site's config, so Drupal can change a module's default too.

`DruxtWrapper`'s element leaves off an attribute the module was given empty, so a server render writes no `style=""`. A contract's `wrapperAttrs()` gives attributes, such as classes, to the root of a wrapper with one root element. `DruxtWrapper` joins those classes to the site's, each once. An `id` or a `style` the site sets replaces the module's whole. It takes them as its `moduleAttrs` prop, apart from the site's, and when the module renders no children, it doesn't render an element for them. A module with `wrapperAttrs()` keeps its element around content even when the hook returns no attributes, so its structure never depends on a setting such as `druxt.classes`. A class the site sets on the module or on `DruxtWrapper` itself keeps the element, as before.

`druxt.classes` decides which of Druxt's classes the default output has: `true` for every class, the default, `false` for none, giving bare semantic markup, or the parts and modifiers to keep. A plugin rewrites them with `defineDruxtClasses()`, which runs on the server and in the browser alike. The naming rules and `resolveDruxtClasses()` are in `@druxt/core/classes`, which doesn't import a framework, so a later adapter for another framework reuses them.

The default output names what it renders with anchors, from `@druxt/core/anchors`, which doesn't import a framework: `data-druxt-entity`, `data-druxt-type`, `data-druxt-field` and `data-druxt-delta`, four frozen names, with `data-druxt-langcode` on an entity's root. `findAnchor()` finds an element by them. `druxt.anchors` is `'dev'` by default, on in development and off in production. A module that needs them turns them on in production with `requireDruxtAnchors()` from `@druxt/core/kit`, unless the site sets `false`, which wins with a build warning naming the module and its reason. The state settles once every module is in, reaches the `druxt:anchors` build hook and `useDruxtAnchors()` in the app, and the Settings section of the development tools shows it. `DruxtWrapper` puts a module's anchors on its element with its classes.

`Druxt` and `DruxtWrapper` register globally and sync, so neither renders inside an async wrapper instance. `DruxtDebug`, `DruxtAuthLogin` and a site's own `Druxt*` components stay lazy, so each loads with the page that uses it. A module renders its default output in place, as `DruxtWrapper` rendered it, when the site gives it neither a wrapper nor attributes and it has no root attributes of its own. The markup is the same, and a field's module instances fall from four to one. The entry chunk grows by the components it now holds, and the page loads fewer scripts.

`cache.content` keeps every server response in the process cache, not only the index: entities, collections, views and route lookups, for as long as Drupal's `Cache-Control` allows, each area bounded by `cache.maxSize` bytes across its consumers, 50 MB by default, the least recently used going first. A request with credentials, the site's own token cookie among them, skips it. A store read with `bypassCache` skips it too and fetches afresh. Its answer replaces the stored entry when it may be kept. A 404 or any other answer removes it. An older request resolving later never replaces the fresher one. An editor's write through the proxy drops the entries for the saved resource, its type's collections, every JSON:API Views result, as a listing doesn't name the entities it shows, and the route lookups on that process. The clear route stays bundled, at `POST /api/_druxt/cache/clear`, and `druxt:cache:clear` still reaches every hold. The parity half of 0.25.0's server cache.

`useDruxtAnonymousClient()`, from `@druxt/core/server`, gives a server route a client that reads Drupal as a visitor.

Under pnpm, `nuxt dev` works without adding the module's CommonJS libraries to your own dependencies.

BREAKING CHANGE: install `@druxt/core` in place of `druxt`. The module runs on Nuxt 4 and Vue 3 only, the store is Pinia, and the options-API `DruxtModule` and the mixins are gone from core. v-model is `modelValue` only. The private runtime config keys `druxtAuth`, `druxtCache` and `druxtBuild` are now `druxt.auth`, `druxt.cache` and `druxt.build`, and the environment variable names are unchanged. The cache clear route moved from `/_druxt/cache/clear` to `/api/_druxt/cache/clear`, so a Drupal Purge purger, or anything else that sends the clear, needs the new path.

Core needs Nuxt 4.4.4 or later, and declares it as a `nuxt` peer dependency. CI tests that floor as well as the workspace's own Nuxt.

`getResource()` waits for a request already in flight for the same resource with another query, unless the store already answers, so a second reader of one entity, such as a standalone field beside its entity, is answered from the store. A request with the same query is shared, its failure included.

The proxy reads `druxt.baseUrl` from the runtime config for each request, so a build pointed at another Drupal with `NUXT_PUBLIC_DRUXT_BASE_URL` sends the browser's JSON:API, file, token and userinfo requests to the same Drupal as the server. They went to the build's Drupal before. The JSON:API is proxied under the language prefixes Drupal is configured with, such as `/english` for `en`, and a default language with no prefix is served unprefixed. `getLanguages()` returns each language with its prefix, and `getLanguagePrefixes()` returns the configured prefixes. A Druxt module proxies a path of its own with `addDruxtProxy()` from `@druxt/core/kit`. The proxy streams request bodies. Drupal's redirects reach the browser, with a location on Drupal's base URL moved to the site, and its cookies are set for the site's host. The forwarding headers come from the site's own view of the request, and any the browser sent are dropped. Behind a front proxy the site trusts, `proxy.trustForwarded`, or `NUXT_DRUXT_PROXY_TRUST_FORWARDED` at runtime, passes that proxy's forwarding headers on and adds the visitor to its `X-Forwarded-For` chain. The proxy sends Drupal no header meant for one hop: `Connection`, a header it names, `TE`, `Trailer` or a `Proxy-` header. It is private runtime config, never sent to the browser. The build reads the prefixes without credentials, once for every module, and a failed probe falls back to the langcode with a warning. A read Drupal refuses, such as with the wrong build credentials, stops a production build with `DRUXT_E01008`. A Drupal that does not answer warns once, as any failure does in development, and the proxy then serves only the unprefixed endpoint. It reads the anonymous index first, so a site without the language module costs one request and no sign-in. Druxt's own server routes sit under `/api/_druxt`, `DRUXT_API_BASE` from `@druxt/core/routes` and `@druxt/core/kit`, and answer before the proxy, so a Drupal that serves JSON:API at `/api` keeps them. The proxy sends Drupal no path under `/api/_druxt`, and answers 404 for one that no Druxt route takes, such as a `GET` to a `POST` route. A session cookie that doesn't decode, such as a bare `%`, counts as none, so the request goes on anonymously. In the browser, a session marker cookie that doesn't decode reads as signed out. A JSON:API endpoint at or under `/api/_druxt`, with or without a language prefix, fails the build with `DRUXT_E01006`.

A contract's `wrapperTag` names the element `DruxtWrapper` renders for the module's root, `div` when not set. `druxt.classes` has a `form` part for a form's classes, with the `form` and `widget` elements, and core's development stylesheet styles the form. The `input` class part is gone. `filterFieldMarkup()`, from `@druxt/core/markup`, which doesn't import a framework, filters a field's description as Drupal's `FieldFilteredMarkup` does, keeping its allowed tags and safe attributes. A protocol-relative `//host` URL names another host, so it goes. A development error names its code, `DRUXT_E` and five digits, a two-digit space per package and three in it, and core's README lists each code with what to do.

A note a contract's `restore()` adds in the browser attaches to its module in the development tools.

`getLanguages()` marks the default language, the one Drupal answers in at the unprefixed endpoint, with `default: true`. It reads each language's configured prefix from `language.negotiation` when the decoupled_settings module publishes it, and the client on both sides gets the map, so a module's langcode reaches Drupal under the prefix it is served at. `druxt.endpoint` is read with one leading slash and no trailing one wherever it is used, so `api`, `/api` and `/api/` name one endpoint for the proxy, the language read and the client alike.

The store's `addResource()` and `addCollection()` take `partial`, so a module seeding a view's rows records the fields each holds, and a later read of another field fetches it. A resource with no self link is still stored. An included resource, at any depth, is stored with every field, so a sparse read of it comes from the store. The store doesn't keep Drupal's `links` on resources, relationships or collections, so a page's payload doesn't name backend URLs. What Drupal omitted is kept as its reason and the omitted types and ids.

In development, the page's client and the server's clients warn once per resource type when Drupal omits resources from a response, and the Druxt DevTools Requests section marks that request as partial, with Drupal's reason.

`resolveFileUrl()`, from `@druxt/core/files`, which doesn't import a framework, resolves a Drupal file URL for the site: on the site through `proxy.files`, else absolute on the new `druxt.filesUrl` or on `druxt.baseUrl`. A static build marks itself in the public config, so its file URLs are absolute, and warns once with `DRUXT_E01002` when `proxy.files` is on.

`resolveFileUrlsInHtml()`, from `@druxt/core/files`, resolves the file URLs inside markup, such as an editor's inline image.

A contract's `empty()` hook says when the module has nothing to render, from its data, such as a menu with no links. While it answers `true`, the module renders only a comment in place of its wrapper, its default slot and its element. A class, an `id` or a `wrapper` option the site set is dropped with it, without a Vue warning. A default slot the site passes still renders with the module's props. It is read at render, so it follows the data. A wrapper's markup never depends on whether it is a functional component or how it is registered.

`useDruxtPageTitle()` holds which component owns the page's title, so a page renders one `h1`. The first to `claim()` it on a page renders the title, and a full-mode `DruxtEntity` claims it too. The claim travels in the payload and starts again on a client navigation to another path. A claimant claims for its own page's route, so a page that is leaving, or kept alive, never takes the new page's title. The claim is let go when its owner unmounts or is deactivated. A claimant needs a setup scope, and development warns when the composable is called without one.

`createDruxtConfigHold()`, from `@druxt/core/server`, holds site configuration read from Drupal once per build and key in Nitro storage until a Druxt cache clear, with shared concurrent reads and a window for a failed one. A hold's name, with no colon or slash, keeps its keys apart from another's, and a read of `undefined` is held as `null`. Each consumer clears its own hold on the `druxt:cache:clear` Nitro hook, as entity does for Drupal's date formats, which it holds under the name `date-formats`.

`druxt.static` is the static mode, for a site served with no Drupal at run time. Unset, it follows `nitro.static`, which `nuxt generate` sets. It switches the file URL rule and the prerender manifest together, and marks the build static in the public config, with `druxt.static.files` and `druxt.static.hybrid`, which `useDruxtStaticBuild()` reads. The build writes the manifest, `/api/_druxt/prerender.json`, listing the pages it generated and its redirect pages by source. The build prerenders Drupal's published pages, every published node and taxonomy term under its language's prefix, unless `druxt.static.routes` is false, and fails, naming each type and language, when it can't list one. This is new: a 0.x static build generated only the pages Nuxt's crawler reached by following links. The crawler still runs, so `druxt.static.routes: false` builds as 0.x did. `druxt.static.routes` also takes a list of the resource types to prerender, strings or RegExps, for a site that renders only some of its node and taxonomy term types. The `druxt:prerender` build hook gets the set of paths for a module or the site to change. `druxt.static.files` keeps a public file's URL on the site and copies each file a page names into the output, so a static site shows its images with no Drupal at run time, and warns with `DRUXT_E01005` about a file Drupal did not answer.

`resolveEntityFields()`, from `@druxt/core/fields`, decides the fields an entity request asks for from the display's fields, what each wrapper reads and `query.schema`, with no framework, so a React adapter resolves them as the Vue one does. `getModuleComponents()` is exported from `@druxt/core/runtime`, for a module that needs its wrapper candidates' names before it renders.

The store's `peekMeta()` gives the `meta` of the document a resource came in, such as what Drupal omitted, with no request. A stored resource's includes skip the resources Drupal already denied, and omitted links are read against the client's JSON:API path. `clearCache()` forgets the denials, and storing a resource forgets its own, so an include Drupal grants later is read again.

`useDruxtLanguages()`, auto-imported, gives the site's languages and their URL prefixes, as the build read them, and the default language, the one served with no prefix, which is the language of every unprefixed page.

A wrapper that declares `druxtRootless: true` renders inside the module's element, which carries the module's classes and anchors and the site's attributes, so a wrapper with no root of its own doesn't leave an attribute with nowhere to go. A contract hook reads the resolved wrapper's name from `ctx.wrapper`, and the component registered under it, the site's when the site registers one, from `ctx.wrapperComponent`.

`druxtLink()` renders an internal link through a custom `NuxtLink` around Druxt's own `a`, so no router active class reaches it, and a module's own classes and `aria-current` show which link is current. An `onClick`, `onPointerenter` or `onFocus` passed in its attributes runs before its own, and a click whose default the handler prevents stays on the page. A contract's `restore()` returns `false` when the stores lack what the payload names, as another page's shared prerender entry gives, and the module reads again, once per instance and key. A read whose inputs moved on while it ran is dropped. Without a wrapper of the site's, a view with exposed filters or an empty area now renders its form or its empty text, where it rendered nothing.

Editing is core. `@druxt/core/edit`, which doesn't import a framework, holds the draft model, one draft per entity and language. A draft holds the pristine resource and the edits as a field-level patch, with the changed fields, the errors keyed by their pointer, the status and the write in flight. Pure functions build the JSON:API write from it and apply a saved resource back. `useDruxtEditStore()`, auto-imported, is a Pinia store over it, shared by every editor on the page. Drafts survive navigation and never reach the payload. `clearCache()` keeps them, and `clearCache({ drafts: true })`, which a sign-in and a sign-out run, closes them. A save goes to a destination, Drupal's JSON:API by default, through the client the editor gives, or one a module adds with `defineDruxtEditDestination()`, and a saved resource goes into the core store, so every module reading the entity renders it. A save to a destination no module added doesn't run, and development logs `DRUXT_E01003`. The store calls the `druxt:edit:start`, `druxt:edit:save` and `druxt:edit:cancel` app hooks. A save that a destination staged elsewhere is `ok` with `status: 'staged'`, and one its `canSave()` refused is not `ok`, with `reason: 'refused'`, in the hook and from `save()` alike. `findDraft()` and `anchorOf()` take an element's anchors to its draft. `useDruxtEditing()` answers `denied`, `unknown` or `allowed` for the session, `druxt.editing` turns editing off or names the default destination, and `DruxtEditControls` is where an editing module renders its controls.

A save and the edits made while it runs don't overwrite each other. A discard during a write clears the edits and leaves the draft `saving` until the write ends, so a new entity is never sent twice. A draft edited while a destination took it is sent again by the next `saveAll()`, and a field set back to its old value during a save stays an edit. `saveAll()` sends a new entity only while an editor holds its draft, and reports one that nobody holds as `skipped: 'unheld'`. A save that a cache clear overtook publishes nothing to the core store.

When Drupal refuses a production build's read of the site's languages, such as with the wrong build credentials, the build stops with `DRUXT_E01008`. The site would otherwise route and proxy only its default language. A build that can't reach Drupal warns once and builds with none. Any failure in development does the same.

Drupal's address is left out of the pages when the browser has no use for it. That is a static build with `static.files` and without `hybrid`, or a server with `proxy.api` and `proxy.files`, where no sign-in sends a visitor to Drupal. `druxt.filesUrl` counts for the files in both. The page then holds only the path Drupal is served under, and the browser's client takes the site's own origin. The server keeps the whole address.

Each package declares the Node versions it runs on in `engines`, `^22.19.0 || ^24.11.0 || >=26.0.0`, which are Nuxt 4's. The repository's own `^24.11.0` is for building the packages.
